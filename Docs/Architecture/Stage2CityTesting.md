本阶段沿用 a29d585 的工具、种子7919和 `Temp/CityScenarios/grid500-normal-final/initial.hcity`，不另建引擎。依次独立提交岗位冷启动、分区重建、垃圾诊断、真实窗口和3000人扩展。

## 批次1：首次岗位分配

原调用 `CityCorePopulation.FindJobs → World.EstimateResidentSeconds → DispatchRoutes.Get → AccessRouting.Find → Network.Route`。每次精确估计最多搜索四组出入口方向，并构造路线，500人首步原有33781次 RouteSearch；住宅-工作地点去重仍不足以控制全候选寻路成本。

现在使用一次同步调度内的 `ResidentRouteBounds` 查询：缓存各实际入口及对向入口的几何位置、读当前路网最高速度，以最小直线距离/最高速度求通勤下界。完整连续行驶路径不短于直线距离，速度不超过最大值，所以只有下界已超过当前精确最佳值时才能排除候选。保留全部技能、真实岗位空缺、资金/道路条件；没有搜索半径、岗位数上限或减少居民。按下界排序只是更早取得可证明的上界；精确评分、同分时最小Job ID均保留。

数据属于冷查询，不是路线或就业事实。生命周期限于一次FindJobs，不能跨道路/入口编辑使用；不写存档或增加长期缓存失效负担。道路模块负责几何下界，人口模块负责岗位规则，交通运动、经济和视图未改。

### 证据

基线与优化分别完整运行同一存档72000步、30日：

| 指标 | 基线 | 岗位优化 |
|---|---:|---:|
| 首步 ms | 2281.700 | 513.600 |
| 首步分配 MB（十进制） | 868.764 | 197.040 |
| 全步均值 ms | 0.271650 | 0.260991 |
| 全步 P99 ms | 1.1496 | 1.1872 |
| 稳定非日界均值 ms | 0.233509 | 0.248338 |

这是冷启动优化，整体均值仅改善3.92%，稳定段/P99没有证实收益，不能称整个城市持续提速77%。两组先后运行，受桌面环境波动影响。

独立采样组首步：RouteSearch从33781次降至1401次，路线查询685次；Population约58.54ms，RouteSearch约41.73ms。剩余ZoningRebuild约377.27ms/174.75MB，已成为冷步主要成本。本批不把它一起改掉。
