# 十万人城市物流归因：货车能交付，城市仍不能经营

2026-10-16。产品源码基准 `df5ba1f`（道路模拟实现仍是 `b7c73c2`）。本批只增加离线诊断与报告，未改变交通、物流、生产、工资、消费、时钟、道路或场景布局。以下距离均为**世界单位**，未校准为米；早期原始诊断字段名 `Metres` 不代表现实米制。

## 结论与证据边界

不是原来的12辆货车永久死锁。4辆原料车、8辆成品车全部正常交付，载荷经实际到达结算进入建筑。主要经营断点是：

1. **单进口口只有4个在途任务名额**，服务8334家工厂，长途运输在整个旅程中占用名额；它不是“每秒处理4车”的口岸吞吐。
2. **空间尺度、运输速度与经济日长不匹配**。三条初始远程进口路线即使完全无拥堵也需要151–191模拟秒，而一天只有120秒。成品路线自由流118.44秒，实际207.05–244.20秒。拥堵进一步放大已有的长运输周期。
3. **商品到货前，商店现金已耗尽**。后续没有付薪出勤，零售 `Open` 条件不成立；有货也无法开店，没有购物任务、零售收入或家庭消费，形成经营上的自锁。

不能把CPU优化说成物流周期修复：加快一帧的计算不会改变一趟运输相对游戏日的长度。也不能以原12车全部到达推断全城无拥堵；最终仍有551个超过一天的任务，最长356秒，其他车辆未逐一归因。

## 吞吐、距离与日长

实际网格跨度约1728单位，限速12；忽略路口，横穿就需144秒，已超过一天。三条远程进口端点最短路线分别1815.15、2293.28、2173.02单位，自由流151.26、191.11、181.08秒；第四条近程388.82单位/32.40秒。端点静态路径是同规则下当前网络的自由流参照，不是从已经换道改写的RoutePlan前缀反推出历史全程。

当前一天120秒、8小时工作段40秒、17点至19点10秒。即使消除全部拥堵，1421单位的这趟成品运输仍约23.69游戏小时。没有偷偷更改日长、速度或活动窗口。

续跑240模拟秒，原料累计交付16→83，只有67份新增，平均33.5份/游戏日；初始4车各载8份且全程占用进口名额。生产8→42，最终仅6家工厂曾生产。一个进口口覆盖8334家工厂明显不足，但“加几个口就解决”同样没有依据：当前33336家庭每天最多一次、每次最多3件，是上界100008件/日，不是已测出的实际需求。与33.5份原料/日差几个数量级。必须先确定消费目标和供给预算，再用入口数、合法路线、车队和实际载荷兑现；不能凭空加货或承诺4个口即可支撑整城。

现有Trade已支持多个合法外部端点。当前场景只构造西侧一组，属于场景供给配置限制，并非缺少一个“多口系统”。Trade依确定性工厂游标/端点顺序采购；Logistics恢复原商店顺序而非按运输距离选店，8334家商店不是天然的本地市场分配。原8车都是1件/车，是有一件就派出而非等待8件聚合；允许上限8不等于实际满载。这些都是独立的业务调度选择，不应伪装成等价算法优化。

## 为什么已经有货，仍没有消费

第一笔新增商品是另一批任务301905在tick7310（365.5秒，第4天约01:06）把6件送入商店5188；原8件最早tick7451到5186，最后tick8354到齐。两店最终库存分别18/8，合计26。

但tick7201、第一笔商品到货之前，两店现金已经为0：

|商店|已托管采购款|已发生工资|当时库存|现金|付薪在岗|
|---|---:|---:|---:|---:|---:|
|5186|990|896|0|0|0|
|5188|360|1526|0|0|0|

5186在原失败tick4800尚有现金673.913、采购托管360、工资852.087。后续新增采购和工资消耗了周转金，而没有商品销售回款。这里不是付款或工资丢失，现有企业、居民、托管与税款校验均通过。

当前因果链直接对应代码：`JobFunded`要求雇主cash>0；`CityCoreResidents`拒绝/结束无资金岗位的出勤；`CityCorePayroll`只将实际付薪劳动计入staffed；`CityCoreConsumption.Open`要求该店有staffed员工。因此“无钱→无付薪出勤→不开店→无销售回款”在当前规则下不能自行恢复。

第4天购物时间内35个有库存样本中，两店Open始终false；同时有18588–30164个家庭满足年龄、在家、存款、当天未购物等前置条件。并非没有购买者，也不是库存未刷新；购物阶段在“没有可营业的有货商店”处就返回。没有发出Shopping任务，所以既没有购买、携货返家，也没有消费。

这不是主张删去真实到岗要求、免费雇工或给企业补贴。经营自锁需要显式产品取舍，不能用改诊断或伪造销售解开。

## 建议方案：待确认，尚未实施

建议按下面分批，不混成物流、经济、时钟和表现的一次重写：

1. **先做同人口的区域供给对照与吞吐预算**：复用现有多个合法端点/施工命令，另存带明确标签的十万人多中心、多外部入口场景；原失败城市不替换。先保持所有经济/日长/车队/载荷参数，量出只改变入口分布能改善多少、还缺多少吞吐，不把换布局称算法提速。需改场景构造器/配置与诊断，正常城市领域模型可不改。仅加少量入口不承诺城市健康。
2. **再独立评估本地采购/供货策略**：用可达性与真实路线成本选择附近入口/商店，保留稳定ID同分规则、实际支付和实车交付；不把最先注册商店当全城默认市场。候选/路线成本为可失效派生数据，入口、路网、建筑变化时更新；不能让经济系统遍历World内部占用布局。涉及Trade/Logistics候选与匹配的明确行为变化，需要确认，不称等价性能优化。不同时改车辆运动。
3. **独立确认时间与周转资金规则**：选择空间/速度/日长的设计基准，使正常区域运输与工作、购物窗口相容；根据真实周转周期审议采购预留和初始经营资金/欠薪或关闭规则。暂不选定新数值、不给旧失败城注资、不改时钟，不把参数调整算算法收益。保持“实际劳动/货物/资金”的事实链。
4. **物流方案确认后，下一性能批次转三万人真实Unity窗口**：分别测Advance与欠步、车辆同步、其他视图、渲染线程/GPU和GC。评估保留全部欠步的每帧计算预算，明确响应性/模拟倍率取舍；本批没有实现或承诺其收益。

每一正式行为改动分别从固定初始保存/明确新场景检验，保留安全、动态施工、在途恢复、钱货守恒与业务活性；性能同宿主同输入隔离配对。既不能因守恒通过称经营健康，也不能因调整业务规则结果不同删断言。
