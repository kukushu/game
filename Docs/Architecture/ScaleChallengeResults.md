# 十万人阶梯挑战：实际结果

## 批次1：有界逐条路线淘汰（2026-10-16）

基线b1bfa97。DispatchRoutes原4096条容量满后调用Reset，一并清空客运/货运蓝图。改为合计仍≤4096的侵入式LRU：命中只移动已有节点，满时仅移除一条最久未使用项；正/反向和客运/货运键不变，路径计算未改，车辆仍独占可编辑Plan。网络对象变化、入口编辑和施工仍整批失效，这是正确失效，不等于容量淘汰。

模块影响：仅DispatchRoutes和可选诊断计数；无业务字段、时钟、城市保存变化，无新增权威事实或业务依赖。LRU在普通游戏默认编译生效，不是benchmark特供；结构额外节点最多4096个，每次查询平均O(1)哈希/链表维护，实际路线数组仍有内存成本，不能宣称“缓存零内存”。

新增RunBoundedCityScenario管理既有Runner的进程树、时间/停滞/内存限制。普通/采样不并行。初次监督器因JSON数字键序列化失败，但子模拟正常结束；原资源CSV保留并明确恢复元数据（不虚构退出码）。已修复为字符串键，并验证600秒正常结束；另实测10秒期限安全结束自己子进程树。强停不保证内存状态保存，已有初始/在途文件和刷新日志保留。OS采样峰值为进程树观测，不等于城市净内存或瞬时峰值。

下一批：检查两种合法出发方向均已占用时的廉价预检；不能把“其中一边堵住”当作全部不可出发，也不能趁优化改选一条不同道路。之后修万人城支管并推进规模阶梯。


## 批次2：服务车辆出发前的方向与空间预检（2026-10-16）

垃圾服务可以使用建筑入口的两个方向。PrepareTransport在寻路前检查两侧真实占用，并用现有静态可达性判断哪些出发方向确实能到目标；只有所有可达出发方向均被堵住才提前拒绝。无路仍报告NoRoute；存在另一条空闲长路时仍执行原最佳路线选择，不趁优化改变派车规则。严格保留1.5间距边界、换道双车道占用、目标两个方向、单行和动态网络失效。Reachability本身有缓存和冷构造成本，并非免费。

## 批次3：合法万人城市与真实规模边界

原168半宽测试城市在修复重复支管后仍缺合法沿路建筑用地（约1550栋时失败，保留failure.hcity）。管线修复仅在原预览非法时连接最近现有物理管段，正常碰撞、费用与最终完整供给不变，不绕开校验。

显式测试配置mature-grid-10000：建设半宽264、平坦地形半宽336、11×11路口网，正常新游戏仍168/240原地形。CityMapState v3表示测试平面，地图是唯一范围事实；管线规划/校验、建筑/分区校验读取同一范围，不在各网络另存边界。存档布局仍城市16，保存自身地图范围，普通CLI Player按该范围生成测试地表。原道路/交通规则、公司资金、垃圾参数、住房8户上限未改。30000/100000配置文件只是待挑战输入，不表示通过。

增加可选构造观察回调，按阶段/批次记录累计耗时与分配，不在高频模拟中捕获宿主状态；构造失败保留最近真实部分城，文件增长供资源监督器识别进度。构造首次21.826秒、累计分配7.137GB，累计分配不等于常驻内存；其中建路约15秒/1.379GB，后续设施/合法放置也有高成本，尚未优化。相同种子重新构造初始保存完全相同。

### **重要失败：城市业务停滞，不是万人健康通过**

最终生产71、消费17、原料到货80，垃圾生成126473/处理960/待收125121。67场站共201服务车；40200派车检查中35858次车队满，处理场99.44%运行时间为空。已完成169次收集/120次返场，单次8单位；返程存储阻塞0，不支持“焚烧吞吐不够”的结论。

从最终城另做1200正常固定步、逐步检查每辆车物理位置：**1934/1934辆初始活动车整60模拟秒完全不动、零任务退休、零消费和垃圾处理**，分属返家675/购物689/货运35/垃圾201/上班334；无车位于LaneConnection。城市发生了全网停滞。守恒与存档正确不能替代通行活性，当前不能宣称支持健康万人城市，更不能宣称十万人流畅。

此为明确可复现交通/布局问题，后续需追踪队首阻塞与循环依赖，不能提高车队/库存/企业钱来掩盖。30k/100k后续测试必须分别标明构造、计算、业务活性，不把人口初始化当产品达标。

模块影响：地图范围只改变基础设施、保存验证和测试视图的必要读边界；Builder/Runner属于诊断层。没有第二份城市人口、库存或物理位置，没有接回旧RoadEdge交通。存档/输入原文件未删除或覆盖。
