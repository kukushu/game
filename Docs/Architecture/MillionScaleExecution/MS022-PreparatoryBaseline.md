## 经营健康与CPU分开

既有[十日调查](MS021-TenDays.md)是模型24000固定步，不是十日真实Player。本轮不重跑昂贵十日，不修改经济规则。原结论仍为经营健康FAIL：

- 8334工厂共用一个进口口、最多4车/批8；十日原料172发出、145到达，是供给/运输能力问题，不能靠放宽物理提高FPS。
- 企业现金约2667万降至32万，工厂现金约1.84万，累计工资约2302万；有库存商店中出现现金0、无员工、不营业。累计消费仅2件，不能当健康需求已满足。
- 垃圾生成1,331,757，待收1,284,565，在途8,312、存储25、处理38,855，账目平衡但服务积压。
- 8145个同任务车辆端点配对中1543辆419.95模拟秒后路线/游标/距离相同，说明无净进展；不是连续轨迹证据，不能直接宣称全部死锁。

后期有货营业店不足，会让消费CPU自然降低。这是业务异常对负载的影响，**不是优化收益**；本窗口结论仅对同城同Tick状态成立。

## 下一步建议（不在本轮实施）

1. **居民全员判断与失败准入的重复工作**：持续成本最高。沿既有MS006—013通知/顺序约束，用100k工作量重新评估已受控的按时唤醒，不直接开启旧30k实验，也不减少真实出行。
2. **增长轮次的统计/需求/格子读取，以及垃圾派发碰撞尖峰**：目标是减少周期性重复全局工作，保持Tick、优先级、账目和业务频率；分别测量，不通过错峰改变规则。
3. **车辆移动与车辆表现同步**：前者约4.8ms诊断成本，后者约5.1ms普通帧成本；检查原增量占用/稳定顺序和未变化显示更新，保留交通安全。随后补Unity表现层剩余约14ms的可靠Profiler归因。
4. 寻路仍有个别28ms尖峰，但本稳态平均约0.6ms；不继续优先围绕购物A*做常数级调优。经营侧原料吞吐/企业现金/垃圾服务应另立规则审查，不能混成CPU优化。

MS-015优化不是运行本测试工具的技术前提，故本预备调查可先做；原任务依赖仍保留。MS-022完整规模、长期健康与可交互验收未完成。
