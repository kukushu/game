# MS-005: employer to resident dependencies

Base7047a7d; original formal baseline93d97f2. CityEntities owns building→HashSet<CityMember> and member→building derived indexes. They reference original members, never copy employment or wages. CollectEmployees sorts only the affected employer's members by current Members.Ordinal (O(K log K)); hash traversal is never business order. Average binding maintenance O(1), storage O(occupied members + employers). Ordinal compaction does not invalidate reference membership.

Resident.jobId, CityJob.buildingId and occupiedCitizenId now have explicit saved-fact setters and a unique owner. Direct writes, AssignJob/ReleaseJob, SyncJobs, constructor and cold restoration all update the dependency. Intermediate two-sided assignment writes remove/reinsert derived membership but never execute business rules; internal observers only invalidate. SyncJobs still rebuilds its original authoritative jobs dictionary; the dependency rebuild walks occupied jobs, not a second unemployed-resident pass. Removed records detach, new sessions rebuild and saves do not persist indexes. No simulation scheduler uses the index yet.
