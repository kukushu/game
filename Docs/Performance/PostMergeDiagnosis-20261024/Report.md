### 1. 最大的持续浪费：商店付不起货款，却反复完成运输准备

沿调用链：`CityLogisticsSystem.Step → CitySimulation.RequestFreight/Dispatch → World.PrepareTransport → DispatchRoutes.Get → CheckAdmission → CityCoreIndustryBusiness.Depart → CommitAdmission`。

为避免猜测，追加一个独立诊断Player，在原分支条件上只加整数计数（`freight-dispatch.csv`）：

- 货运尝试1950806次，运输准备成功1950806次。
- 商业规则拒绝1950494次，**全部命中原来的 `shop.Account.Cash < cargo * price` 条件**。
- 成功提交312次。99.984%的尝试在准备完成后被拒绝；不是路不通、入口占用或预约拒绝，八种入场拒绝计数均0。

原规则每5步调度一次，按既定商店顺序尝试；某店没钱而未成功后继续尝试，下一调度期再来。`PrepareTransport`已经查询路线、检查实时占用/预约并创建TripTask、Shipment、Vehicle和可编辑路线副本，之后才发现商店现金不足。这是实际调用链和计数共同确认的浪费。城市无限建设资金不等于商店账户无限现金。本轮没有给商店加钱、删掉检查或改变目标选择。

Profiler导出121个CPU帧（120观察帧及边界）里，Admission约218777次、累计分配171.77MB，货运阶段157.66MB。`CityFreightCandidates.Collect`约87.77ms/4388次，远小于货运阶段约921ms；主要问题不是单纯候选列表筛选。不要把相互包含的分配或耗时相加。

### 2. 最显著的长帧：建筑入口登记会清空所有普通路线缓存

原生Profiler帧14：PlayerLoop453.73ms，模拟424.51ms，其中Logistics360.65ms。该帧货运下面1960次Dijkstra累计350.75ms，居民另外14次约1.27ms；GrowthBoundary28.27ms，分区显示Build24.62ms。**350.75ms是同帧多次搜索的合计，不是单次Dijkstra。** 见 `long-frame-scopes.csv` 及原始导出的 `profiler-hierarchy.csv`。

代码依据：`CityCoreGrowth.AdvanceGrowth`建筑完工后调用`World.RegisterAccess`；该方法无条件`dispatchRoutes.Reset(Network)`，`DispatchRoutes.Reset`同时清空全部freight/passengers字典与LRU。即使道路Network没有变化，新建筑登记一个入口也使已有建筑对的普通缓存失去复用。本次窗口普通LRU容量淘汰计数为0，不能误称4096项缓存装不下；上述批量搜索出现在同一增长/分区更新帧，与这条调用链吻合。**清空的确切调用时刻未另加事件日志，因果定位依据是现有调用链与同帧采样，不是已做过取消失效的优化对照。**

这与垃圾基地缓存是两回事：本轮13763次原始Dijkstra的追踪depot均为0/other，属于居民/普通货运，不是垃圾算法未启用。采样前缀中原始RouteSearch约405ms，其中货运351.32ms/1960次、居民53.16ms/156次、外贸0.72ms/4次。

### 3. 垃圾车道树有效，但64MiB预算造成持续缓存抖动

Release 50×窗口：17673查询、17552命中、121未命中/淘汰、438棵树重建，入口/路网失效计数0。归因窗口：14420查询、14332命中（99.39%），88次未命中/淘汰、320棵树重建，涉及96个基地；持续驻留88个基地，记账66958848字节。

本图9508条Lane，每基地保守预算`9508*80+256=760896`字节，64MiB只够88个；这不是128基地条目上限先耗尽。96个实际活跃基地轮流查询，已预热的项被淘汰后仍需再建树。因此继续等加载/预热不能消除这种稳态重建。

归因窗口去程166棵/1532.10ms，返程154棵/1480.48ms，合计3012.59ms，占Step约17.00%；单棵最高17.63ms。垃圾服务查询总3273.81ms，减去其中建树约261.22ms（Step约1.47%，包含路线恢复及诊断）。**真正已热查询本身不是第一瓶颈；反复重建却不能当成加载成本排除。** 本轮没有调大缓存预算或改算法。

Profiler帧101还出现垃圾出车58.55ms，其中6棵去程树累计58.02ms；这是另一类可重复游玩长帧。上次路口Dijkstra报告的“0淘汰、0重建”不能套到现在的车道方案。

### 4. 居民与交通仍有全局工作

居民阶段约16%，其中Job检查1546万次约816ms；车辆运动约16%。占用索引清桶、收集和排序合计1921.30ms，分布在居民派车/移动等阶段。车道树不会优化这些工作，也不会优化普通居民和货运路线。本轮没有改模拟对象数量、车辆物理、就业、经济或固定步。

## 渲染、GC与内存

道路63720逻辑Drivable已合批到425Renderer；正常Release道路Mesh约85.12MB、2746106三角形。暂停时60FPS、最长17.11ms，说明当前固定全景下持续显示不再是首要瓶颈。

原生Profiler导出：DrawBuffersBatchMode全体渲染提交平均约0.36ms/暂停CPU帧、0.33ms/50×CPU帧；ExecuteRenderQueueJob约0.019/0.030ms。它们是全部可见渲染的标记，**不是道路独占耗时**。渲染线程大量Semaphore.WaitForSignal是等待，不能把它的时间当作道路绘制CPU。UI约0.6–0.9ms/帧，车辆显示约0.3–0.4ms/帧；增长时仍有单次分区Mesh更新24.62ms，Release最长帧对应结构同步可达约54ms。

Development窗口约1.64MB托管分配/帧、25秒约1.88GB累计分配；不是驻留内存增加1.88GB。GC次数17（Mono三代显示相同，不相加）；原生短采样GC.Collect合计约7.82ms，不足以把453ms采样长帧归因成纯GC。没有可靠的全窗口完整GC暂停总量，Release逐帧分配计数器不可用，保留-1。输入到输出工作集峰值含加载/预热/写档，不冒充稳态驻留或树独占内存。GPU计时不可用，不报告虚构的GPU毫秒。

## 为什么50×仍达不到

50×要求每现实秒完成1000个0.05秒步；本次普通Player约239步/秒。7161步累计真实宿主模拟推进20546.81ms，即约2.87ms/步（未插入Core归因）。即使忽略画面等成本，按这段工作量也需要约2.87个CPU秒/现实秒才能完成1000步；这是当前成本的解释，不是对其他城市的理论性能承诺。

8ms预算在完整步执行之后检查，不能中断已开始的360ms货运/几百毫秒模拟任务。正常组最多8步/帧，未触及32步上限。只把上限和预算放到128步/32ms，实际仅15.91×，FPS降到19.80、P99升到454ms，证明不能靠解锁倍率解决。所有欠步继续保留，存档原来约126029秒积压也没有丢弃；暂停不自动消耗欠步，倍率按实际完成步数计算。

## 下一步建议，按当前证据排序

1. **消除失败货运的重复准备。** 在不改变商店顺序、现金条件、实时入场检查和成功提交原子性的前提下，研究纯只读业务资格预检，避免为已确定无法付款的目标创建车辆/路线副本。应先做新旧完整业务/交通状态对照，不能通过加钱或少发货获得性能。
2. **收窄普通路线缓存的失效范围。** 优先确认新增独立建筑入口为什么必须清空原有建筑对；保持网络/原入口变化时的正确失效，避免增长事件触发全网普通Dijkstra突发。它更直接针对当前半秒长帧；实际可节省多少需实现后配对验证。
3. **解决96基地与88驻留预算的矛盾。** 先测保守记账、实际驻留/临时内存与活动工作集；再选择合理预算、共享或更精确的树生命周期。不能只盯99%命中率忽略重建成本，也不把增加内存说成算法复杂度下降。
4. 随后研究居民重复Job检查、占用桶更新/排序；再处理增长导致的分区显示长帧。本次没有证据支持重新大改道路渲染或再次更换垃圾热查询算法作为首选。

这些是待验证的优化方向，未给出未实施方案的FPS收益承诺。
