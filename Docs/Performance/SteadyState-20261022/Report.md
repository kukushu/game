## 为什么仍有约200ms长帧

平均CPU占比与长帧来源不同。普通Release最长204.54ms，其中当前Update模拟140.22ms、结构显示同步47.73ms；关闭道路后仍有203.40ms长帧，说明这些停顿不靠道路绘制优化就能消失。

原始Profiler在相同城市固定步位置捕获到：

- tick146521附近：一帧3步的Step累计219.65ms，其中**单次GrowthSearch217.63ms、分配34688628 B**；其内部GC.Collect两次累计5.50ms，不能把整个长帧都归咎于GC。正常Release双消融在同tick附近也测到191.35ms帧、模拟180.23ms，证明不是只有Profiler才会停顿。诊断版217ms不能当成正常版的精确耗时。
- tick146761附近：模拟160.82ms，Growth123.76ms；其中分区占用62.22ms、增长搜索54.24ms。模拟外另有分区占用21.09ms和 **`City.Views.Zoning.Build` 24.61ms / 16437328 B**，与该帧约46ms结构同步相符。

调用链核对：`CityCoreGrowth.AdvanceGrowth` 在约234k格子上多次LINQ过滤、枚举候选足迹和重叠；`HarborCityZoningViews.Sync` 虽已局部重建64单位Mesh块，但每次仍**重新遍历可见格子、分组所有块并创建列表**，不等于显示更新完全局部。以上代码解释与实测样本相符，不是仅凭代码推定它占多少时间。稀疏同步也会触发持续分配和GC。

GC：归因窗口约482633 B/帧、Boehm收集计数增加3；Release计数器不可用，保留-1。原始样本支持增长/分区分配是风险，但未测得完整窗口所有GC暂停总量，不能把统计代数相加当成暂停时间。精选长帧真实调用树在 [profiler-spikes.csv](profiler-spikes.csv)。

## 表现层：97120个道路View的成本在哪里

同样完全预热后，在暂停城市中比较正常道路和仅关闭道路Renderer的raw。每段请求120帧，导出121帧，剔除首尾边界后**各119帧**。关键小样本也保留，避免阈值过滤把控制组误写为0。

| CPU标记/线程 | 正常道路 ms/帧 | 道路Renderer关闭 ms/帧 |
|---|---:|---:|
| `DrawBuffersBatchMode` / Render Thread | **15.810** | **0.120** |
| `ExecuteRenderQueueJob` / Main Thread | **4.057** | **0.016** |
| `CullObjectsWithoutUmbra` / Main Thread | 0.107 | 0.00039 |

道路对象是独立GameObject/MeshRenderer，共享材质但仍有大量独立网格提交。两种控制使相同城市暂停FPS从34.11到60.03，支持主要是**Renderer的渲染队列处理、批次提交/驱动侧工作**，不是97120个道路MonoBehaviour各自执行Update。正常稳态没有道路拓扑变化，也没有持续重建道路Mesh；不要把热点误判为 `RoadViews.Sync` 每帧全重建。

Render Thread和Main Thread会重叠/等待，**不能把15.81+4.06直接当帧耗时**。`DrawBuffersBatchMode`含驱动交互，仍不能严格拆出GPU等待；GPU帧计时不可用，未证明全部是GPU算力瓶颈。View数量也不等于实际draw call数量，相关计数器缺失列保留-1。道路关闭达到目标60FPS，控制受帧率上限限制，不代表真实渲染只需16.7ms。

暂停raw的 `Profiler.FlushMemoryCounters` 约10.88ms/帧，是原始采样开销，**不是正式游戏热点**，不计入道路成本。UI约0.63ms、车辆显示同步约0.17ms；目前不该优先重构HUD或车辆View。raw仅记录主/渲染线程，虽然导出器允许Job.Worker，本次实际捕获未提供这些工作线程，不能据此声称已完整量化所有线程。

## 为什么到不了50×：预算、帧数和突发步共同作用

50×要求每秒 **1000个0.05秒完整步**。正常组约485步/秒，平均每帧15.68步，最大24步，从未达到32步上限；619帧中618帧模拟推进达到/超过8ms。32→128步上限后仍24.25×，所以主要限额是**时间预算**。8ms是完整步后检查，重步不可中断，平均实际推进11.12ms/帧；正常组约0.709ms/步，若工作分布相似，1000步需要约709ms主线程CPU/秒，当前时间预算下只实际投入约344ms/秒。

还存在一个被实际数据验证的宿主调度效应：`CityPlayerStepBudget.Request` 将临时执行credit夹到 `maximumSteps×0.05`。长帧期间产生的请求可能超过上限；超出部分**仍完整保存在SimulationClock欠步中，但不会保留为等量的宿主credit**。因此后续帧并不会自动无限追赶已积欠时间。逐帧重放现有Request/Complete公式，与实际步数完全一致：

| 对照 | credit触顶帧数 | 被夹掉的宿主credit（模拟秒） | 窗口末credit |
|---|---:|---:|---:|
| 正常8ms/32 | 618 | 514.291 | 0.750 |
| 正常32ms/128 | 34 | 77.338 | 0.948 |
| 道路关闭32ms/128 | 15 | **38.070** | 0.009 |

最后组38.070/20.005约 **1.903倍** 的执行额度损失，解释了即使放宽预算、关闭道路，仍只有约48.08×而非稳定50×的主要差距。边界请求时长与采样墙钟略有差别，不能强行写成精确50减1.903。完整credit恒等式 `请求秒 - 完成秒 = 被夹credit + 末credit` 误差小于1e-7；真实模拟欠步的独立账时也全部通过。[pacing.csv](pacing.csv) 可核对。

这不是模拟时间被丢弃，也不授权改成跳步。credit损失是预算/长帧导致吞吐不足在宿主记账中的表现，不是额外CPU开销，不能与预算损失重复相加；没有修改credit策略并宣称其收益。当前宿主是在响应能力和追赶欠步之间做限制；将8ms直接改32ms虽提高倍率，却把正常画面降到26.60FPS、P99变差，**不能当作本轮优化结论**。未来若调整调度，也须保留唯一时钟、0.05固定步、欠步和UI响应，单独验证。
