## 结论与范围

原审查的循环结构判断基本正确，但不能据此把它们列为当前最大热点。本轮从正式 `b2a333d9944b2029c8f4998276487fb8edcde4c8` 建立 `codex/optimize-matching-indexes-20261102`，只实现建议中的前两个小改动，并补上实测发现的入口重绑缓存错误。运行代码为 `a7d664c`、`c0fff65`，测量工具为 `e04114f`。**未完成持续维护的待求职/空缺岗位/补货需求集合，不标记MS-016或MS-019 DONE，也不改变其他MS任务状态。**

普通Release十万人中景FPS 56.88→56.97、实际倍率2.844×→2.851×；只有单对20秒，不能认定整体提速。现有两个存档的800步诊断中，实际岗位分配与货运候选收集均为0；优化入口没有被触发，不应把分项加速包装成当前游戏的大幅收益。该计数窗口与普通Player窗口Tick范围不同，不能当成普通Player全窗口精确调用统计。

## 改动与所有权

|位置|修改|保留的约束|
|---|---|---|
|CityJobs.RegisteredJobApplicant / AssignJob|已建索引时用Member、Family直接查找，核对同一Person实例、同一家庭、resident及该家庭people.Contains；未建索引时保留列表查询|资格、年龄、技能、资金、岗位占用、在途/在岗拒绝及原计算/提交顺序不变|
|CityEntities.IndexType / UnindexType|新增内部派生ShopRevision，仅商业建筑列表增删/替换时递增；替换仍遵循原移除再追加的商店顺序|不持久化、不改商店或账户事实；家庭/居民/非商店增删不使该版本改变|
|CityFreightCandidates.Refresh|缓存键为Network引用、NetworkGeneration、ShopRevision、AccessRevision|保留所有真实路网/入口失效；Collect的遍历、可达性、排序及原商店顺序不变；付款和运输事务完全未改|

归属校验从最坏O(家庭数+家庭成员数)变为两次字典查询加O(该家庭成员数)，刻意保留局部Contains而不是删除校验。冷初始化仍可扫描家庭。货运减少的是无关变更引起的重建；一次真正重建及每家工厂的全候选收集复杂度尚未改变。新增两个int版本槽，不增加第二套账户、岗位或居民事实，也没有为索引建立全城状态副本。

**同时修复旧漏失效：** 若删路后查询过候选，再以RebindAccess恢复入口，World可复用Network并替换RoadAccess；AccessRevision没有随该提交改变，但NetworkGeneration已改变。旧缓存仅看Network对象引用，会漏掉恢复的商店。冻结基线的独立可达性测试真实失败，保留日志 `before-rebind.log`；新版本使用已有提交代次，测试通过。未修改World事务、版本递增、寻路或经济规则。该错误路径下新版会恢复原应合法的候选，后续派发可能与旧错误缓存不同，不能宣称该路径请求序列仍完全相同；正常未触发旧缺陷的对照如下。

## 分项实测：不是整城FPS

.NET10 x64 Release，同一30k/100k存档，串行A/B/B/A，每进程预热1000次后记录5组，原始各组（含首组JIT扰动）全部在[Components.csv](Components.csv)，表中为中位数。初版/曾与编译等活动交叠的试跑留本地，不用于此表；最终分项在所有其他自建测试结束后串行执行。

|分项|三万人旧→新|十万人旧→新|
|---|---:|---:|
|10000次原岗位分配入口调用|149.69→1.44ms|1133.50→1.47ms|
|上述调用托管分配|240000→0B|240000→0B|
|50轮无关换户并收集货运候选|42.51→19.18ms|124.04→82.96ms|
|上述候选索引重建次数|50→0|50→0|
|上述分配|13185600→3200B|41628000→3200B|

分配入口微基准取当前执行序中最后一名有岗位居民，反复调用其原岗位，确认事实未变；偏向较长的原家庭查找，**不是10000次新就业，也不是全员平均分配成本**。货运微基准在测试副本中换户后换回，仅用于证明无关失效；它不是自然游玩频率。计时包含换户通知和Collect，排除索引身份检查/独立oracle；没有消除Collect本身的可达商店扫描与排序，稳定无变化查询也未声称加速。
