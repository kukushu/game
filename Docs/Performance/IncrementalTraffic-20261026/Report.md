## 改动及不变量

原来的 `MoveStep` 提交位置后标脏，下一次发车/占用查询或移动触发 `Reindex`：清空所有历史桶、重新登记所有车体/变道影子及物理预约、全桶排序。到达清退几乎每步发生，也无条件标脏。将调用移到其他业务不能节省这个共享成本。

现在 `World` 独占派生索引，权威位置仍在原 `Vehicle.Position`：

- `CityRoadCoreOccupancy.cs` 维护车辆已登记车道、变道影子、待更新车辆和脏桶。移动提交只登记实际锚点变化；查询前移除旧成员、更新距离并只排序脏桶。排序仍使用原比较器。
- 发车按原顺序插入，变道开始直接登记影子，到达清退直接移除；服务续程重新计算预约，不强迫重新登记全城占用。施工、恢复、入口/结构变化、直接Freeze仍保留原完整重建及验证。
- **物理路口预约及活动计数仍逐车重建**。移动阶段存在临时预约，不能把旧临时声明跨步保留下来。因此这次不是完整O(变化量)索引，保留了一个O(车辆数)安全阶段。
- 另有仅保存车辆引用的ID有序运动列表：读取时排序一次、单调ID发车时追加、清退时稳定压缩。先从原占用快照收集全部限位，再按原ID顺序生成意图、推进、提交和到达；取消每步意图排序。原权威车辆列表顺序和变道Choose顺序不变，乱序存档也有对照。
- 无第二套位置、业务或存档事实。缓存不保存；单线程、0.05秒步长、发车/重试/经济/货物/垃圾/寻路/预约/8ms及32步预算不变。

原占用登记/排序每步处理全体车辆及历史桶；新桶处理约为变化车辆加脏桶排序，但预约仍O(N)。运动意图排序从每步O(A log A)变成O(N+A)有序扫描；N为当前保留任务车辆，A为活动车辆，仍不跳过任何实际移动。

## 剩余瓶颈与集成判断

建议集成本轮两个小阶段：正确性对照未见行为差异，真实窗口平均收益重复出现；用户四个未提交文件和原始存档保留。仍不把这当成所有交通或施工长帧已解决。

1. 物理路口声明重建仍O(N)，下一轮若进一步增量化，必须区分实际身体与本步临时预约，保留当前oracle证明等价。
2. 意图限位仍须读取原占用快照，逐车推进/变道判定仍存在；本轮没有修改运动规则。
3. 居民调度和其他业务仍消耗大部分完整步；约9.50ms平均步仍常超过8ms渲染帧预算，50×目标下通常一帧只能跑一整步。约49FPS×0.05秒即约2.45×，少数两步帧略提高倍率。没有提高预算掩盖成本。
4. 原城市增长等约100ms尾帧仍在，50× P99无改善。没有继续扩展到事件居民调度、道路重建或寻路等其他系统。
