## 原因及改动

旧 `CityCoreGrowth.AdvanceGrowth` 对3种用途、每用途10种尺寸，反复执行同一个 `candidates.Where(row0 && available && use)`。本真实城市没有可用的对应用途起始格，30次空搜索仍检查4,742,100次谓词，占约64.5ms；叠加普通业务和显示形成约100ms帧。

新实现在第一次有需求且没有同用途待建项目时，**一次按原Cells顺序筛出三种用途的可用沿街起始格**，尺寸搜索复用各自有序列表。无候选直接结束该用途；无有效需求则不创建分组、不扫描。候选只活到本轮调用结束，不保存、不跨步缓存，没有失效协议或第二套分区事实。

保留用途次序、尺寸轮换/nextProjectId、格子次序、地块平均位置、全部几何/占用/碰撞/入口查询和项目结算。分组在完成到期项目并取得最新Cells之后建立；后续同一同步规划过程中，CanPlace等查询不改变Cells的用途/可用快照，新增项目仍参与原CanPlace拒绝规则。没有更改居民、寻路、垃圾、经济、车辆、路口预约、渲染或0.05秒/8ms/32步预算。

复杂度：原空搜索约O(用途×尺寸×C)，新约O(C+各尺寸实际候选访问)。代价是每轮O(K)临时候选引用（K为匹配可用沿街格），没有长期内存。若原实现首个候选就成功，新实现仍先扫描一轮全表，这类场景不保证单次搜索更快；活跃增长与多用途选择的正确性已对照，小城整体业务回归通过，尚未为所有大规模有效分区分别做Player性能配对。
