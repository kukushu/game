# 居民请求循环诊断：先量重复工作，再评估事件调度

结论：**有大量重复岗位读取，但不能把此前的30.6%全部归因于居民遍历，也不能直接当成事件调度收益。** 三万人同城三轮对照中，仅在一次居民判断内复用岗位和工作地点，判断段由 **4.62降至3.93ms/步，减少15.0%**；完整模拟步CPU由11.64降至10.89ms，减少6.46%。这是Temp中的诊断消融，不是已发布的游戏优化。纯遍历加第一层资格过滤的冻结状态校准仅约0.37ms/步，不能仅更换循环容器就期待大幅提速。

## 时间拆解：实测与估计分开

三轮相同完整城市、相同600步：

| 每固定步，三轮均值 | stock | 只复用本轮岗位/工作地 | 减少 |
|---|---:|---:|---:|
| 整个模拟步 | 11.644ms | 10.893ms | 0.752ms，6.46% |
| 居民请求整段 | 6.694ms | 6.017ms | 0.677ms，10.11% |
| 其中真实RequestCommute流程 | 2.073ms | 2.089ms | 无稳定改善 |
| 剩余遍历、资格、读取及通勤估算 | 4.621ms | 3.928ms | **0.693ms，15.00%** |

消融只在第一层过滤通过后取一次`ResidentJob`，从同一对象取得工作地点；原条件、班次计算、资金资格调用、派发顺序和重试时间保持不变。未缓存资金状态、未跳居民、未减少尝试；三组分别省0.484、0.834、0.761ms/步的非派发判断时间，不能把均值当所有城市保证。

**当前最可靠的两部分界限是：重复岗位／工作地读取的可消除净成本约0.69ms/步，去掉它后仍有约3.93ms/步的必要读取、资格判断、通勤估算与循环。** 后者不是纯枚举，前者也不是所有岗位读取的总成本。

为进一步解释量级，原生Player在最终状态后执行只读批量校准，见`read-calibration.csv`、`loop-calibration.csv`。纯枚举约0.30ms/三万人；枚举加原第一层过滤约0.37ms。Workplace/ResidentJob/GetBuilding约20.45/19.25/14.48ns/次，ShiftStart/ShiftMinutes约6.38/1.54ns/次。按实际调用次数粗加，工作地、岗位、建筑类型与班次合计约1.9ms/步，其中班次两个操作仅约0.2ms/步。

这些是**冻结状态、热读批量校准的量级估计**，不是在真实交错调用中测得的独占时间。包含委托/循环和JIT优化影响，控制操作约4.7ns且不能对不同操作一概相减；不能用1.9ms与4.62ms相减就宣称剩余全是纯条件分支。循环+资格的低开销实测和读取复用A/B才是主要决策证据。

## 事件驱动：有潜力，但应排在小改动后

只有0.385%的循环访问走到RequestCommute，重复检查很多。但若只省枚举和第一层过滤，校准量级仅约模拟CPU的3.1%；要取得更大收益，必须连同后续大量资格、读取及通勤缓存查询一起避免。

把stock非派发居民段4.62ms全部假设为零，整步最多省39.7%、CPU吞吐理论上限约1.66倍。这是不可实现的零开销上界：必要派发、安全检查仍在，事件维护、失效、批量唤醒都需成本。**本次未实现事件调度，不能给它填写实际FPS、50×倍率或确定收益。**

正确性风险主要是漏唤醒和时序变化：

1. 时间不仅有班次起止，还有日切、浮点retryAt、visitUntil，以及自由流估算和实际lastCommute共同决定的提前出发时间。失败发车仍按原规则重试，不能靠减少重试次数冒充收益。
2. 岗位分配/移除、建筑用途、家庭迁居、死亡/健康/canWork、资金从零变正或变负、道路/入口版本、到达和在途恢复都可能改变资格；只监听班次是不够的。
3. 现顺序为边界增长/人口后处理居民请求，随后生产、消费、货运、垃圾、移动与到达结算。不同阶段的变更必须在原本可观察到它的居民阶段生效，不能一收到事件就提前派车。相同固定步中仍需保持原Members顺序，否则入口占用、路线准入和任务先后可能改变。
4. 拆路失败事务不能留下唤醒；已失效/重复事件不能重复派车；读档应由唯一居民/岗位状态重建派生调度，不新增第二套权威状态。多人因班次或雇主资金同时唤醒时仍可能形成长步，不能用跨步延期改变业务。

推荐先单独实施、回归验证本轮已经量出收益的本轮读取复用；再专门细分剩余资格/通勤缓存成本。之后若做事件实验，应先影子记录应唤醒集合，对跨日、资金变化、到达、失业、病亡、拆路回滚及冷恢复逐步对照，再测队列开销和批量唤醒。不建议现在直接替换整个居民调度。
